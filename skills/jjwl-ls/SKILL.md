# 九江文旅线上质检（jjwl-ls）

把《九江文旅质检规则》里的红线口径固化成可执行规则，对 AI 接待通话全量自动判定，
输出「不合格通话 + 证据原话 + 优化动作」，让人工只复核真正有问题的通话。

本 Skill 的所有命令都基于本文件所在目录（下文记为 `jjwl-ls/`）。相对路径都相对该目录。

## 何时用本技能

- 用户要求**巡检/质检**九江文旅、庐山景区的 AI 通话记录。
- 用户想找出「AI 处理不好的通话」「答错的通话」「踩红线的通话」。
- 用户要统计门票优惠讲漏了、AI 编造金额、口吻不像客服等问题。
- 用户提供了通话记录表（xlsx），要求出一份质检结论或报告。

## 核心口径（来自文档，必须遵守）

文档《九江文旅质检规则》明确 5 类必须关注的问题：

| 优先级 | 问题 | 规则 |
|---|---|---|
| 红线 | 景区政策类、时间日期类未按口径回复 | R05 |
| 红线 | 超出知识范围，AI 联想生成日期/金额/路线/活动 | R04 |
| 红线 | 回复口吻不符合客服身份（骂人、嘲讽、质疑、吵架） | R03 |
| 红线 | 输出内部流程节点、"依据知识库""依据内部政策"等语言 | R02 |
| 红线 | AI 沉默不回复 | R01 |
| 红线 | 身份/金额/日期不符仍给优惠 | R15 |
| 红线 | 户籍资格判断错误 | R16 |
| 红线 | 乱给索道/观光车优惠 | R17 |
| 红线 | 年龄优惠口径说错 | R18 |

规则全集见 `references/rules.md`（18 条）与 `质检规则说明.docx`。

其中 **R05 是最容易踩、也最重要的一条**。文档原文要求：

> 回答门票与优惠问题时，必须完整输出与用户问题相关的对应条款**全部要点**，
> 不得总结、压缩、合并或省略**适用对象、活动日期、资格条件、所需证件、票价、
> 适用范围、办理及预约方式、限制和提示**。一个问题涉及多项政策时，逐项完整说明。

也就是说：AI 只说了「深圳居民 80 元」还不够，漏掉「不含观光车、索道等二次消费」
就是不合格——这正是文档点名的「省略限制和提示」。

## 工作流程

### 第 1 步：拿到通话数据

三种来源，任选其一：

```bash
# A. 用户已给导出文件（最常见）
--input 呼入通话记录.xlsx

# B. 直接查线上数据（走 DLC 只读取数，需本机有 data-sanhuo 凭据）
--company-id 90867 --robot-ids 2161410 --days 7

# C. 纯规则自检，不需要业务数据
--demo
```

若用户只给了 Excel，**不要**先纠结字段名：`load_calls()` 已容忍
`通话记录id/通话记录` 等常见别名。缺列时会明确报错并打印真实表头。

### 第 2 步：跑规则自检（必做，先于任何结论）

```bash
cd jjwl-ls/scripts && python3 -m jjwl_qc.selftest
```

必须看到 `35/35 通过`。这一步含多条「应判合格」的反例，用于防止规则改动引入误判。
**自检不过就不要出结论**，先修规则。

### 第 3 步：巡检

```bash
cd jjwl-ls/scripts
python3 -m jjwl_qc.cli --input /path/to/通话记录.xlsx --output /path/to/outputs/日期
```

输出三个文件：

| 文件 | 用途 |
|---|---|
| `质检明细.json` | 每通电话的结论、得分、命中规则、证据原话、优化动作 |
| `质检汇总.json` | 总量、不合格率、红线通话数、按规则的问题分布 |
| `质检报告_<日期>_<时段>.docx` | **Word 报告（主交付物）**，标题与文件名均带时间 |


生成报告：

```bash
python3 -c "from jjwl_qc.report import render; \
render('outputs/质检明细.json','outputs/质检汇总.json','outputs/质检报告.md')"
```

### 第 4 步：抽样复核（不可跳过）

规则只做筛选，**结论必须人工确认**。对每一通判为不合格的通话：

1. 打开原文，读完整对话；
2. 确认命中的规则是否真实成立（重点看 R05 的「缺失要点」是否真的影响游客决策）；
3. 若判定有误，记录是规则误报，而不是直接把结论改掉了事。

向用户交付时，**说明哪些结论已人工复核、哪些是规则初判**。

## 判定口径

- **红线**：一票否决，得分 0。
- **扣分**：累计后 < 80 分判不合格。
- 每条结论都附证据原话与轮次，可回溯原文。

完整规则（每条对应的文档原文、判定逻辑、不判定的边界）见
[references/rules.md](references/rules.md)。

## 关键设计约束（改规则前必读）

1. **宁可漏判，不可误判**。质检误伤会直接摧毁可信度。只在证据充分时判定。
2. **R05 判定范围是整通对话**，不是单句。游客可能分几次追问，AI 也分几次回答；
   只看单句会把「分步解答」误判成漏项。
3. **条款匹配只用区分性实体**（地区/人群/景点）。「庐山」「九江」「门票」这些词
   几乎出现在每个条款名里，参与匹配会让任何问门票的问题都错配到「音乐节条款」。
4. **AI 已正确兜底的不算漏项**。回复中出现「无法确认 + 引导小程序/人工」即视为合规，
   不要求它编出答案。
5. **重复追问只判问句复读**。陈述句重复属于可接受的信息重申；转接播报不算复读。

## 扩展

| 想做的事 | 改哪里 |
|---|---|
| 加一条红线 | `scripts/jjwl_qc/rules.py` 加 `rule_xxx`，在 `inspect()` 注册 |
| 调整词表（景点/人群/红线词） | `scripts/jjwl_qc/lexicon.py` |
| 政策更新 | 替换 `assets/` 下的提示词与知识库，重跑 `python3 -m jjwl_qc.facts` |
| 回归用例 | `scripts/jjwl_qc/cases.py`，新增后必须 `selftest` 全绿 |

## 交付话术

给用户的结论应包含：
- 纳入多少通、不合格多少通、不合格率；
- 每通不合格的**证据原话**和**为什么算问题**（引用文档口径）；
- 具体优化动作（改话术、补知识库、修链路）。

避免只说「不合格率 X%」而不给证据——业务方无法据此改进。

## 定时巡检（12 段/天）

线上已部署定时任务 `com.dsh.inbound.pull`，每天 08:00–19:00 每小时运行一次，
其中 08:00 抓「前一日 19:00–当日 08:00」跨夜段，共 12 个数据文件。

### 时段切分

| 段 | 触发时刻 | 统计区间 | 说明 |
|---|---|---|---|
| 1 | 08:00 | 前一日 19:00 – 当日 08:00 | 跨夜合并，13 小时 |
| 2 | 09:00 | 08:00 – 09:00 | |
| … | … | … | 每小时一段 |
| 12 | 19:00 | 18:00 – 19:00 | |

合计：1 个跨夜段 + 11 个整点段 = **12 段/天**。

### 运行链路

```
launchd(08:00–19:00 每小时)
  └─ run_window.sh
       ├─ ensure_session.mjs   校验并自动重登登录态
       ├─ pull.mjs <start> <end>   调平台导出接口抓 xlsx
       └─ 质检（jjwl_qc）
            ├─ 质检明细.json
            ├─ 质检汇总.json
            └─ 质检报告.md      ← 每个时段一份独立报告
```

### 产物位置

```
~/Library/Application Support/dsh-inbound/
├── output/呼入记录_<起>_<止>.xlsx          原始数据
└── output/qc/<YYYYMMDD>/
     ├── 质检日报.md                        ← 当日跨时段汇总（每次跑完自动刷新）
     └── <段号>_<时段>/
          ├── 质检明细.json
          ├── 质检汇总.json
          └── 质检报告.md                  ← 该时段独立报告
```

**报告层级**：每个时段一份独立报告（12 份/天），外加一份当日汇总日报。
主交付格式为 **Word（.docx）**。**禁止产出 Markdown 报告文件。**
日报含分时段趋势表、问题类型汇总、重点时段提示，每跑完一个时段自动刷新。

单独生成日报：

```bash
cd jjwl-ls/scripts
python3 -c "from jjwl_qc.report import render_daily; \
render_daily('~/Library/Application Support/dsh-inbound/output/qc/20261111')"
```

### 运维命令

```bash
# 立即跑一次当前时段（验证用）
bash ~/"Library/Application Support/dsh-inbound/run_window.sh"

# 查看调度状态
launchctl list | grep inbound

# 查看日志
tail -f ~/"Library/Application Support/dsh-inbound/logs/pull.log"

# 手动补跑某时段（先抓再质检）
cd ~/"Library/Application Support/dsh-inbound"
node pull.mjs "2026-11-11 10:00:00" "2026-11-11 11:00:00"
```

### 定时任务注意事项

1. **登录态会自动重登**：`ensure_session.mjs` 在 Cookie 失效时用账号密码重登，
   失败则跳过本次并在日志留痕（退出码 3）。
2. **导出是异步任务**：`pull.mjs` 创建导出任务后轮询进度，最长 15 分钟。
   若超时会失败，下一小时会重新抓该时段。
3. **抓取失败不写报告**：`run_window.sh` 在取数退出码非 0 时直接结束，
   不会用旧数据生成误导性报告。
4. **固定播报不算复读**：开场欢迎语、转接提示、录音告知属平台固定话术，
   重复播报不判 R12，否则会大面积误报（这是实测踩过的坑）。

### 完成度自检与告警（必需）

定时任务「跑完」不等于「出了报告」。曾出现过取数成功但质检模块导入失败、
日志只显示 `fetch done exit=0`、当日一份报告都没出的情况。

因此必须保留完成度自检：

```bash
cd ~/"Library/Application Support/dsh-inbound"

python3 health.py                  # 体检：应完成/已完成/缺失
python3 health.py --json           # 机器可读
python3 health.py --repair         # 补跑缺失时段
python3 health.py --alert          # 有缺失时写 ALERT.json
```

**判定口径**：时段结束后 5 分钟才计入「应完成」，避免跑在数据落库前误报。

**产物**：
- 体检日志：`logs/health.log`
- 告警文件：`output/qc/<日期>/ALERT.json`（恢复后自动清除）

**部署了两个 launchd 任务**：

| 任务 | 触发 | 作用 |
|---|---|---|
| `com.dsh.inbound.pull` | 08:05–19:05 每小时 | 取数 + 质检 + 出报告 |
| `com.dsh.inbound.health` | 12:15、19:30 | 独立体检，缺失则自动补跑 |

体检任务独立存在，是为了覆盖「取数任务整体停摆」——若只靠每次运行后自检，
任务一旦不跑就永远不告警。

### 踩过的部署坑

1. **launchd 读不到工作区路径**（macOS TCC 限制）→ 模块与 assets 必须复制到
   `~/Library/Application Support/dsh-inbound/` 下本地导入。
2. **文件匹配要用精确起止时间**，不能用「最新文件」——重登后异步导出未完成时，
   会选到相邻时段的旧文件，导致报告串段。
3. **relogin 后导出是异步的**，`pull.mjs` 可能先返回，需按目标文件名判断而非取最新。

### 飞书推送（完成后自动发群，超时报警）

**目标群**：九江文旅内部质检测试（chat_id 缓存于 `chat_id.txt`）

```bash
cd ~/"Library/Application Support/dsh-inbound"

python3 notify.py --slot-dir output/qc/<日期>/<时段目录>   # 推送单段报告
python3 notify.py --alert-json output/qc/<日期>/ALERT.json # 推送缺失告警
python3 notify.py --all-pending                            # 推送当日未推送的全部
python3 notify.py --test                                   # 通道自测
```

**触发时机**：
- `run_slot.sh` 每段质检成功后自动推送该段报告
- `health.py --alert` 发现缺失时，由 `health_check.sh` 与 `run_window.sh` 推送告警

**已处理的坑**：

| 问题 | 处理 |
|---|---|
| 告警每次巡检重复刷屏 | 按「日期+缺失时段集合」指纹去重，标记存 `logs/.alert_sent` |
| 报告过长超限 | 按 `#` 标题边界分片，标注 `（i/n）` |
| 消息发送后如何防重发 | 时段目录写 `.notified` 标记 |
| 群消息列表显示已撤回的消息 | 接口返回 `deleted:true` 即已撤回，界面不显示，属正常 |

**发送形式：Word 附件 + 摘要**（这是主交付方式）

每段报告发两条消息：
1. `质检报告_2026-11-12_0900-1000.docx` 文件附件 —— 完整三段式报告
2. 摘要文本（群消息，非文件）—— 通话量/合格率/红线数/问题通话id 一览

**关键前提：bot 必须在群里。**
文件上传走 bot 身份（`--as bot`），因为 user 身份缺少 `im:resource:upload` 权限。
bot 未入群时会报 `230002 Bot/User can NOT be out of the chat`。
拉入方式（群主身份）：

```bash
lark-cli im chat.members create \
  --chat-id <oc_xxx> --member-id-type app_id \
  --data '{"id_list":["<app_id>"]}'
```

`--file` 只接受**相对路径**（拒绝绝对路径与 `..`），实现里会切到文件所在目录再传文件名。

**报告标题与文件名必须带时间**（否则群内多份报告无法区分）：

| 场景 | 文档标题 | 文件名 |
|---|---|---|
| 同日时段 | 九江文旅 AI 通话质检报告（2026-11-12 09:00-10:00） | 质检报告_2026-11-12_0900-1000.docx |
| 跨夜段 | …（2026-11-11 19:00 至 2026-11-12 08:00） | 质检报告_2026-11-11_1900-2026-11-12_0800.docx |
| 日报 | 九江文旅 AI 通话质检日报（2026-11-12） | 质检日报.docx |

跨夜段必须写两个日期，否则会被误认为当天凌晨。
实现见 `docx_report.py` 的 `slot_report_name()` 与 `_slot_span()`。

## 输出格式硬约束（必须遵守）

**所有报表、文档一律输出 Word（.docx）。禁止生成 `.md` 报告文件。**

| 产物 | 格式 | 说明 |
|---|---|---|
| 时段质检报告 | `.docx` | `质检报告_<日期>_<时段>.docx` |
| 当日汇总日报 | `.docx` | `质检日报.docx` |
| 规则说明文档 | `.docx` | 由 `scripts/build_rules_doc.py` 生成 |
| 明细/汇总数据 | `.json` | 中间数据，供程序读取，非交付文档 |

群消息里可以发 Markdown **文本**（飞书自动渲染），但**不得**把 Markdown 存成文件当交付物。

**实现要点**：
- `run_slot.sh` 只调用 `render_slot_docx` / `render_daily_docx`，已移除 `render_slot` / `render_daily` 调用
- `health.py` 判定完成只看 `质检报告*.docx`
- `notify.py` 附件发送失败时退化为「摘要文本」，不再读取 `.md`
- `report.py` 中的 `render_slot` / `render_daily` 为历史遗留，可保留但**不得在流程中调用**

规则说明 Word 的生成：

```bash
python3 scripts/build_rules_doc.py 质检规则说明.docx
```

## 推送前复核闸门（必须）

**所有跑出来的有问题的记录，推送前都要重新复核；确认没问题才允许推送。**

复核器：`scripts/review.py`（部署副本在 `~/Library/Application Support/dsh-inbound/review.py`）。

### 流程位置

```
规则引擎初判 → 质检明细.json
      ↓
review.py 复核（推送前自动触发）
      ↓ 确认 → 推送
      ↓ 剔除 → 改写明细/汇总 → 重生成报告 → 推送
      ↓ 存疑 → 标注「复核存疑待人工」→ 推送（附存疑标记）
```

### 复核维度

每条初判问题独立过 4 道检查：

| 检查 | 内容 | 结果 |
|---|---|---|
| 证据回溯 | 证据原话必须能在对话原文中找到（容忍截断） | 失败 → 转人工 |
| 守卫复核 | 该规则的豁免条件是否被正确应用 | 命中 → 剔除 |
| 语境复核 | 证据在原文语境中被否定时不判（如"没法保证"） | 命中 → 剔除 |
| 主题复核 | 用户必须真实询问政策本身，而非顺带提及 | 不满足 → 剔除 |

### 覆盖规则

R01（告别后沉默）、R04/R05/R06（主题真实询问）、R07（否定语境）、
R08（机构转述）、R12（固定播报）、R13（已执行转接）。

### 三种复核结论

| 结论 | 含义 | 处理 |
|---|---|---|
| 确认 | 各维度复核通过 | 正常推送 |
| 剔除 | 疑似误判，证据充分 | 从报告移除，重算分数，留痕复核日志 |
| 转人工 | 证据无法回溯或边界存疑 | 推送但标注「复核存疑待人工」 |

### 产物

| 文件 | 内容 |
|---|---|
| `复核日志.json` | 每条复核的检查项、结论、理由 |
| `.reviewed` | 复核标记（时间戳 + 数量），推送闸门依据 |
| `observations` 追加 | 剔除/存疑原因写进通话备注 |

### 命令

```bash
python3 review.py --slot-dir output/qc/<日期>/<时段>   # 复核单段
python3 review.py --demo                              # 复核器自检（4 用例）
```

### 设计原则

复核器与规则引擎**相互独立**：复核不重新跑规则，而是以"挑错"视角
反向验证每条初判。两边逻辑不同源，才能拦住规则自身的盲区。

复核自检必须全绿（`review.py --demo` 4/4），不过不许上线推送。

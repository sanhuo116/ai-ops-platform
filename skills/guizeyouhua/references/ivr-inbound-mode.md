# 模式B：纯数据侧呼入 IVR 巡检（无话术包）

适用：呼入 IVR 型 bot（按键菜单 + 按键输入 + 核实 + 记录/留言），用户不要求数据以外的渠道。
实战样本：黄埔反诈专线 2251810（租户 91386），521 通 / 9,746 轮，2026-11-11~11-18。

## 0. 用户硬性要求（先读）

1. **通话记录两种来源，二选一**（用户要求，平台已同步实现）：
   - **平台取数**：DLC 呼入/外呼数据表（本文件第 1 节口径）；
   - **用户直接上传**：通话记录 Excel/CSV/JSONL（百应后台导出的"通话记录id + 通话记录"格式
     或 DLC 逐轮格式均可），平台解析成统一 calls 格式后走同一套巡检。
   - 两者择其一即可发起分析；上传任务跳过 DLC 取数阶段。
   - regex-opt-platform 已实现：`POST /api/upload-calls`（multipart 上传+解析预检）→
     `POST /api/tasks/with-upload`（建任务）；新建任务表单有"通话记录来源"单选
     （平台取数 / 上传通话记录），任务详情页标注来源徽标。
2. **取数只用呼入数据表（DLC），不登陆后台**。禁止为"拿话术包"而走 CDP/浏览器导出；
   无话术包时全部结论从通话行为反推。（例外：用户主动上传通话记录文件，属于来源二选一。）
3. 优化正则两条铁律（用户原话）：
   - "参考已有的正则库里面的正则的写法，尽量简单点"（库内写法范本见 `regex-style.md`）
   - "尽量不要移除，而是通过加前后的限制条件进行优化"
4. 结论宁缺毋滥：所有候选先全量语料回验，ASR 误写不补，边界冲突不补。
5. **工具语境识别豁免**：调用按键（DTMF）输入、远程数据查询等工具时，系统默认用户的
   自然语言【不做】匹配识别——这些语境下的识别失败/无响应/没被理睬都是平台默认行为，
   **忽略不计缺陷**。只豁免"纯工具收集"语境（如 DTMF 输入号码）；核实/问答语境 ASR
   是激活的（确认词 150/151 被接受），分支缺失仍要报。实测影响：2251810 的 D1 从
   25 降到 18（按键输入环节 7 例剔除）。

## 1. 数据与还原

- 表：`dwd_call_byrobotprod_inbound_instance_log_di`，条件 `robot_def_id` + `company_id` +
  `dt >= '20261111' AND dt <= '20261118'`（dt 是 '20261111' 字符串格式，闭区间）。
- 拉两份：**内容**（`speaker_type, content, user_mean, knowledge_base_id`）+
  **时间**（同一表追加 `start_time, end_time, duration_ms`）。时间字段用于排除"赛跑/重叠"假设。
- 清洗：空 content 剔除；`条件判断-条件判断节点` 剔除；`<break time="...ms"/>` 剔除；
  按 `inbound_instance_log_id` 排序。
- **barge-in 必修**：连续用户轮合并为"段"再判定（前一个外呼 bot 实测 38.5% 的轮次级错误
  是连续发言伪影）。AI 响应的是整段，不是单轮。
- `user_mean` 是平台运行时语义标签，作旁证：`OK`=肯定、`人工服务`、`AI_UNKNOWN`、
  `~`=实体应答、`*`=未知/填充。

## 2. 语境指纹与路由矩阵

AI 话术写死 → 固定子串指纹分语境；路由 = 段后第一个非空 AI 句（maxskip 6~12，跳过空轮）。

```python
FP = [('主菜单','请根据语音提示'), ('人工忙提示','人工客服忙'),
      ('身份证输入','按键输入您的身份证号码'), ('身份证核实','和您核实一下您的身份证'),
      ('单张多张','单张银行卡冻结还是多张'), ('报案时间','什么时候报案|什么时候开始不能使用'),
      ('派出所','哪个派出所报案'), ('语音记录','说出您遇到的问题|复述一次'),
      ('开场白','这里是黄埔反诈专线')]
```

产出 `context × routing` 矩阵 + examples（键 `ctx||rt`），一切缺陷扫描都建在矩阵上。
无响应 = 段后全程无 AI 话术（多为 DTMF 等待期用户放弃），**本身不是缺陷**，但结合意图就是（见 D1）。

## 3. 正常行为排除（判成缺陷会虚报）

| 行为 | 判定 |
|---|---|
| **纯工具语境（DTMF 输入/远程查询）下说话无响应** | **平台默认：工具期间自然语言不识别，忽略**（TOOL_ONLY_CTXS） |
| 忙提示按 1 → 回主菜单 | 设计：继续等待=回主菜单（实测 65 例） |
| 忙提示按 2 → 语音留言、按 9 → 重听 | 设计如此 |
| 菜单外数字（6/8）无响应 | 菜单无此项，正确不响应 |
| 超时探活"您好。在吗" | 正常探活（用户最后应答→在吗 中位 12.8s） |
| 开场白后回主菜单 / 24 例转忙提示 | 正常（线路忙或用户静默） |

## 4. 五类缺陷与判定配方

### D1 转人工意图未响应（18 处/工具语境豁免后，原 25）
- 人工话语正则：`(转|找|要|请|帮我|给我).{0,3}人工|人工(服务|客服|坐席)|真人(客服)?|接(人|客服)|客服人员`
- 按"语境 × AI 走向"出矩阵：转人工提示=对；继续要信息 / 无响应(挂机) / 回主菜单 = 缺陷。
- **工具语境豁免**：按键输入环节说人工 → 无响应/继续要信息，**不计缺陷**（DTMF 期间
  自然语言不识别是平台默认）。但"工具语境无人工出口"可作为产品建议单独提出，不是缺陷计数。
- 子型①：**DTMF 抢先**——同段里"说人工 + 按键"，AI 响应按键（如按 1 进业务）。段归因后不再误报"语音识别失败"。
- 子型②：语音记录环节说人工被当留言记录挂机（语音记录语境不豁免）。
- 子型③：忙提示后说人工仍继续要信息。
- 82 句人工话术全量验证正则零误伤；豁免后语境分布：主菜单 11 / 语音记录 5 / 忙提示 2。

### D2 菜单数字词误路由（3 处）
- 纯数字词段 `^(一|幺|壹|二|两|三|四|五|六|七|八|九|零|〇)+$` 在主菜单语境的 AI 去向 vs 应去分支。
- 口径：只统计"段内全部为数字词"（混合段不算）。实测"一。"×3 全被支付宝分支抢走。
- 数字词→按键映射缺失是根因；按分支拆七条独立正则（见第 5 节 R3）。

### D3 分支词表覆盖缺口（重问型，47 次）
- 判定：AI 原样重问同一问句 = 上次应答未命中。按重问时用户原话分布量化。
- 实测：单张多张问句后"三张/两张/3张"占重问 24/47（51% 可修复）；"单价/单专/单身"是
  ASR 误写"单张"，**不补**（语义风险>收益，宁缺毋滥）。
- 修复覆盖 = 可修复应答数 / 重问总数。

### D4 探活子节点吞确认词（12 处，via_zaima 全部 true）
- 特征链：核实问题 → ~15s 静默 → AI 播"您好。在吗" → 用户答确认词 → AI 重问原核实问题。
- **诊断对比**：确认词在有/无"在吗"插话时的接受率。实测 13/13 被拒 vs 150/151 接受 → 缺陷锁定在"在吗"子节点缺确认分支。
- 排除两个假假设：含 `*` 号码（19/150 接受 vs 3/14 拒绝，不成立）；时间赛跑（AI 重问
  start_time 全部晚于用户应答结束 1.0~2.8s，零重叠 → 不是 TTS 冲突，是识别窗口/分支缺失）。
- 修复：在吗子节点补确认分支，正则与主核实分支一致（R4）。

### D5 否认仍进流程（3 处）
- **段模型正确形态**：否认发生在业务问句【之前】——用户在主菜单语境说"没有/不是/不用"，
  AI 却进入业务核实（"在办理…业务之前，需要先核实"）。不要拿"AI前句语境=支付宝核实"抓，
  那时否认段还没发生（prev 是主菜单）。
- 否认判定用**搜索版** `(没有|不是|没冻结|不用|不需要)`（barge-in 合并段是混合段，
  孤立锚定版 `^…$` 会全漏）；但**不要**把核实/输入环节的"不是(打错了)"算进来——
  那是号码输错的合理重输，实战中宽口径 12 例全是误报。

## 5. 优化正则产出规则

| # | 规则 | 说明 |
|---|---|---|
| 1 | 库风格简单式 | `^…$` 锚定 + 字符类 + 可选尾标点 `[。，,！？?]?$`；不用复杂嵌套 |
| 2 | 只加不删 | 补词/加前后限制；不删既有规则 |
| 3 | 全量验证 | 每条候选跑全量用户语料：命中数 + top 形态列表作证据 |
| 4 | 边界冲突检查 | 候选不得误伤既有分支语义。例：R2 首版含"几张"，会命中"单张…另外几张…"，去掉后 39 句零冲突 |
| 5 | 按分支拆分 | 数字词按 0/1/2/3/4/5/9 各一条独立正则，不做大合并式 |
| 6 | ASR 误写不补 | "单价/单专"=单张误写，收进来语义风险大于收益 |

## 7. 交付时必须声明的限制

1. 无话术包：分支正则全部为行为反推，上线前需在平台核对具体分支的词表位置。
2. `user_mean` 是平台运行时标签，仅作旁证不作为判定依据。
3. 无响应判定依赖轮次与时间字段；空轮（条件判断行）已剔除。
4. 时间字段 `start_time=0` 的轮（多为 DTMF）不参与时间差分析。

## 8. 脚本使用（scripts/ivr_inbound_audit.py）

```bash
# 先探针看高频 AI 话术，配置 FP/ROUTE 两个映射
python3 scripts/ivr_inbound_audit.py work/<bot>/turns_raw.json --probe

# 正式巡检（--time 可选，拉时间字段用于排除赛跑假设）
python3 scripts/ivr_inbound_audit.py work/<bot>/turns_raw.json --time work/<bot>/turns_time.json
```

产出 `ivr_contexts.json`（语境×路由矩阵+例证）、`ivr_defects.json`（D1~D5 明细）、
`ivr_summary.json`（供 Excel 概览引用）。

2251810 校准基准（FP/ROUTE 为该 bot 配置，工具语境豁免开启）：D1=18 D2=3 D3=47
D4=12(via_zaima=12) D5=3，矩阵 55 条。
人工话语全分布口径 40 处（含同话多段与工具语境）；豁免后逐段主归因口径 18 处——
交付时统一说明口径与豁免规则。

### 脚本实战教训（都是跑真数据踩出来的）

1. **D3 重问判定不能逐字相等**：重问句常不带"好的，"前缀，必须用语境指纹相等判定。
2. **D4 判定要放在"无语境 continue"之前**："您好。在吗"不在语境指纹表里，ctx=None
   会提前 continue，D4 永远是 0。
3. **语境指纹有优先级**：支付宝问句本身含"按键输入您的身份证号码"，必须排在身份证
   输入之前，否则语境错归。
4. **否认词分两个版本**：混合段用搜索版，孤立应答用锚定版；核实环节的"不是"是合理重输。
5. **时间赛跑没排除就归因** → 先比 start_time：AI 重问晚于用户应答结束才可能是识别失败。
6. **工具语境豁免优先于一切缺陷判定**：TOOL_ONLY_CTXS 的 continue 要放在 D1 之前，
   否则工具语境的"说人工无响应"会被误计；但 D4 等核实语境判定不受豁免影响。
7. **每次改完用真数据回归**：2251810 的基准数字就是回归标尺，换 bot 重新校准 FP/ROUTE。

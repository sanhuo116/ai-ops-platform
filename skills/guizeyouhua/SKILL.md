# 规则版话术巡检与正则优化（guizeyouhua）

对百应**规则版**（decision tree 驱动、话术写死）话术做全量巡检：判定每轮用户应答 AI 是否走在正确意图的分支上，产出可执行的正则/知识库优化清单。

**两种模式**：
- **模式 A（有话术包）**：本文件主体描述的流程，依赖 huashubao 导出。
- **模式 B（纯数据侧呼入 IVR）**：见 `references/ivr-inbound-mode.md`。用户明确"取数只用呼入数据表、不登陆后台"时走此模式——无话术包，全部结论从通话行为反推。核心脚本 `scripts/ivr_inbound_audit.py`（先 `--probe` 探针配指纹，再跑巡检出 D1~D5 缺陷+矩阵）。

**通话记录来源二选一（用户规则，两种模式通用）**：平台取数（DLC 数据表）或用户直接上传通话记录文件（Excel/CSV/JSONL，百应后台导出格式或 DLC 逐轮格式），二者择一即可结合话术包分析。regex-opt-platform 已实现上传入口（`POST /api/upload-calls` + `POST /api/tasks/with-upload`，新建任务表单"通话记录来源"单选），上传任务自动跳过取数阶段。

**模式 B 平台默认豁免（用户规则）**：调用按键（DTMF）输入、远程数据查询等工具时，系统默认用户的自然语言【不做】匹配识别——这些语境下的识别失败/无响应/没被理睬都是平台默认行为，忽略不计缺陷。只豁免"纯工具收集"语境；核实/问答语境 ASR 是激活的，分支缺失仍要报。

## 何时用本技能

- 用户给出通话记录 Excel + 话术包（或要求先用 `huashubao` 导出），要检查"AI 是否走对了分支/意图"
- 用户只要求数据侧巡检呼入 bot（按键菜单 IVR：核实/记录/留言），不碰后台 → 模式 B
- 要优化分支关键词、全局分支库、全局问题库
- 要找"知识库死条目""框架外意图""弱肯定误判"这类配置缺陷
- 用户明确说"规则版话术""每个节点话术是写死的"

## 优化正则的两条铁律（用户原话，两种模式都适用）

1. "参考已有的正则库里面的正则的写法，尽量简单点" —— **先学库内写法范本**（见 `references/regex-style.md`）：否定词族 lookbehind `(?<![没不么无否未木].{0,8})`、限量间隔 `.{0,N}`、后向排除 `(?!.{0,5}处理)`、柔性分隔 `.{0,1}`
2. "尽量不要移除，而是通过加前后的限制条件进行优化" —— 只补词/加前后限制，不删规则；放开锚定时必须用 lookbehind 补否定排除

弱肯定改造模板（加首字符排除，不删原式）：`^嗯[，,]?(?![。，,！!？?嗯哦啊呃呢哈呀哦呦嚯嘛吧呗喽咯唷没不无未算别用要也还]).{1,6}[。，,！!？?]?$`

**改写五步法**（详见 regex-style.md）：学范本 → 放开该放开的 → 每放一处补一处否定排除 → V8 全量回归（+增/-减逐条核对语义）→ 边界集固化必跑。三个陷阱：动词消耗（"不需要"的"要"）、lookbehind 紧邻语义（隔字要带 `.{0,N}`）、contains 复核假阳性（用 exec 看命中点）。

所有候选必须全量语料回验：命中数 + top 形态 + 边界冲突检查（例："几张"会误伤"单张…另外几张…"）+ 回测命中率 ≥40%，宁缺毋滥。

## 核心认知（全 session 踩坑换来的，先读这段）

### 1. 话术包的真实结构：业务节点是决策树，不是平节点

一个业务节点 = **一棵决策树**，树里每个节点是一句固定话术 + 它自己的分支集合。
「询问是否安装理财软件」实测 37 条话术 / 46 个分支 / 5 层嵌套。

```
decisionNodeBO.decisionItemList        ← 第 0 层话术
decisionNodeBO.childrenList[i]         ← 第 1 层分支（answerIds[0]=分支名）
    .decisionItemList                  ← 第 1 层话术
    .childrenList[j].decisionItemList  ← 第 2 层话术 …递归下去
```

**教训**：只读顶层 `decisionItemList` 会漏掉 80% 话术（420469 顶层只有 30 条，递归后 372 条）。
**巡检单元是"树节点"（一句固定话术 + 分支集合），不是业务节点。**

### 2. 分支去向在 childrenList[].actionParam

`childrenList[i].actionParam` 是 JSON 字符串，`sceneNodeName` = 目标节点。
`target = None` ≠ 兜底，是**在本节点内顺序说下一句**（树内续说，合法行为）。

### 3. 节点名必须用 sceneNodeName

`decisionNodeBO.name` 通常是类型标签（"普通节点"/"条件判断节点"）。
用 `trees[i].node.sceneNodeId` 去配 `flow.nodes[].sceneNodeName`。

### 4. 全局库映射必须走 answerRegexSide（本次最大返工）

节点字段 `answerRegexSide`（JSON 字符串）声明了每个分支引用全局库的**哪些具名分支**：

```json
{"肯定":["省厅-肯定（中性）","肯定(中性)","肯定（西湖-有下载）"],
 "否定":["否定（中性）","否定（没接到电话或信息）"]}
```

**坑**：本地分支叫"肯定"，全局库里叫"肯定"的分支有 4 个（ID 21/53/118/3910，不同场景），
但真正引用的是 `省厅-肯定（中性）` 等具名分支。**按名称模糊匹配会取错规则集**，
实测导致走向正确率 70.6%（假）→ 79.2%（真），问题数 647 → 638。

正确取词优先级：
```
本地 answerKeywordDef 有 → 用本地（且叠加 regex_side）
本地无 → 按 answerRegexSide 的具名分支逐个取全局库
regex_side 也无 → 才按分支名退化取全局库
```

### 5. 规则版话术 = AI 原文可精确匹配

话术写死不改述，AI 转写文本与话术包原文**精确匹配**（归一化停顿标记和标点后），
命中率 94.9%。剩余 5% 是"您好，在吗"这类系统提示音，直接排除。
**不要用模糊反推**——那是大模型话术才需要的方法。

### 6. 百应正则方言

- 私有量词 `{0<>N}` → 转 `{0,N}` 再 `new RegExp`
- 变长 lookbehind `(?<!(不|没).*)` → Python `re` 编译不了，**必须用 V8/Node**

### 7. 三类"正常行为"必须排除，否则正确率虚低

| 排除项 | 判定 | 实测规模 |
|---|---|---|
| 无判定分支的 step | 只有 默认/原地 分支 = 纯告知话术 | 140,135 次（占 step 72.6%）|
| 节点内顺序推进 | 分支 target=None 且 AI 留在原节点 | 82,291 次 |
| 开场白纯接听 | `^(喂|你好|哎|诶|啊|哦|嗯)+$` 且节点=开场白 | 23,570 句 |

**不要把当前 step 回溯到更早的 step**（会让 errWrong 虚高），无判定分支直接跳过。

## 工作流

### 第 0 步：前置数据

- 通话记录：Excel（通话记录 + 对话逐轮两个 sheet），转成 `dialogue_turns.jsonl`
  （每行 `{id, turn, role, text}`，role ∈ AI/ME）
- 话术包 JSON：用 `huashubao` 技能导出 `bot_{botId}_bundle.json`
- 全局分支库：从 huashubao 的 externalRegex 拿，或 `33023910.cos.byai.com/voice-bot/global-branch-library`

### 第 1 步：解析决策树（scripts/tree.py）

```bash
python3 tree.py   # 读 bot_{id}_bundle.json → flow_tree.json
```
产出每层（flow/multi）的 step 列表：`{node, path, text, edges:[{branch, target, keywords, regex_side}]}`。

### 第 2 步：解析全局分支库

`branch_lib_kw.json`：`{分支名: {keywords: [...], ids: [...], labels: [...]}}`。
**注意**：同名分支会被合并（如 4 个"肯定"），ids/labels 字段保留来源，改动时要精确到 ID。

### 第 3 步：主巡检（scripts/audit_tree.mjs，Node 运行）

```bash
node audit_tree.mjs
```
判定链：AI 话术精确定位 step → 用户回复跑该 step 各分支正则 → 命中分支的 target vs AI 下一句实际 step。

产出：`tree_problems.json`（走错明细）、`tree_gaps.json`（未命中+反推）、`tree_stat.json`。

口径：
- 走向正确 = ok（跳对了）+ okDefault（该默认走默认）+ okInternalSeq（节点内续说）
- 问题 = errWrong（命中分支走错）+ errDefault（该默认偏离）
- noMatch 是"未命中任何分支"，多为叶子话术后应答，不是缺陷

### 第 4 步：知识库两类问题（scripts/kb.py + audit_kb2.mjs）

```bash
python3 kb.py && node audit_kb2.mjs
```

先修数据脏问题：`similarityQuestion` 常是字符串 `"[]"`（空数组字面量），必须视为空。

**问题一（框架内未命中）**：
- 静态：死条目 = 无 keyword 且无有效相似问法的条目（有 target 的是最严重级）
- 动态：命中知识库条目但 AI 未按其 target 推进（被节点分支抢占）

**问题二（框架外意图）**：
- 用语言学可枚举标记判定"意图明显"，不猜语义：
  - 发问词：`什么|啥|哪位|谁呀|怎么了|干嘛|为什么`
  - 诉求词：`能不能|我要报|帮我|报警|投诉|我的钱|能追回|听不到`
- 未命中任何知识库条目 + 有意图标记 = 框架外意图
- 短问句（≤14 字）也算；长陈述句不算（避免把正常作答误判）

### 第 5 步：汇总产出（scripts/build_v8.py + build_v9.py）

问题分 6 类：
1. 命中分支却走错去向
2. 该走默认却偏离
3. 该命中分支却未命中
4. 分支语义疑似配错（样本与分支语义相符率 <35% 时归此类，**不补词**）
5. 知识库命中却未按意图走
6. 框架外意图（知识库无匹配）

**补词建议的门槛（教训）**：
- 纯语气词占比 >55% 的组不补（用户只是应了一声）
- 语义相符率 <35% 的不补，归为"语义配错"报业务
- 所有候选正则必须回真实样本验证命中率 ≥40%，否则剔除
- 实测：某轮挖出 87 条方案，逐条核验后只剩 2 条成立；宁缺毋滥

### 第 6 步：出 Excel

`make_xlsx_v9.py` 产出 9 张表：概览 / 问题明细(7列) / 分支关键词优化 / 分支配置缺口 /
全局库弱肯定误判 / 框架外意图 / 知识库死条目 / 优化效果回归 / 方法说明。

**全局库三合一对照表**（用户要"原版+优化后"时）：
A 原版分支库（全量正则逗号合并一列）+ B 原版问题库 + C1/C2 优化后（逐行标 删/增/补/保留，带证据）+ 改动汇总。

## 判定口径速查

| 术语 | 定义 |
|---|---|
| step | 一句固定话术 + 它的分支集合（巡检最小单元）|
| 走向正确 | 命中分支的 target == AI 下一句实际所在 step 的 node |
| errWrong | 命中了分支但 AI 去了别处 |
| errDefault | 无分支命中、应走默认，但 AI 去了别处 |
| noMatch | 无分支命中（含合法的叶子后应答，不全是缺陷）|
| 死条目 | 知识库条目无 keyword 且无有效相似问法 |
| 弱肯定误判 | `^嗯。$` 类规则把语气词判成肯定分支 |

## 交付话术模板

### 模式 A（外呼规则版，实测样例）

```
36,600 通电话 / 916,378 轮对话，可判定跳转 265,290 次：
  走向正确 210,214（79.2%）
  命中分支却走错 42,113
  该走默认却偏离 12,963

问题明细 6 类共 N 行，其中：
  知识库死条目 127 条（68 条配了去向却永远无法命中）
  框架外意图 4,962 次（哪位/什么/怎么了，AI 照本宣科或直接挂断）

必须声明：通话记录无节点轨迹字段，节点序列靠 AI 话术精确匹配反推（命中率 94.9%）；
规则版话术写死所以精确匹配成立，但系统提示音占比 ~5% 已排除。
```

### 模式 B（呼入 IVR，2251810 实测样例）

```
黄埔反诈专线（2251810，呼入 IVR），近一周 521 通 / 9,746 轮，
确认 5 类缺陷 83 处（脚本口径，工具语境识别豁免已应用）：
  D1 转人工意图未响应 18（含 DTMF 抢先、语音记录环节当留言；按键输入环节按平台默认豁免不计）
  D2 菜单数字词误路由 3（说"一。"全进支付宝分支）
  D3 张数词不识别重问 47（"三张/两张/3张"不在词表，重问率 29%）
  D4 探活吞确认词 12（"您好。在吗"子节点缺确认分支，13/13 全拒 vs 对照 150/151 接受）
  D5 否认仍进流程 3（主菜单否认被无视直接进业务核实）

优化正则 5 组（R1~R5），全库风格、只加不删，全部经全量语料回验（82/39/8/501/5 句）。

必须声明：本次为纯数据侧巡检（呼入数据表），分支正则是行为反推，
上线前需在平台核对具体分支词表位置；按键输入等工具语境按平台默认豁免（自然语言不识别），
"工具语境无人工出口"作为产品建议另提，不进缺陷计数。
```

## 踩坑记录（复现必读）

1. **按名取全局库规则** → 取错场景的规则集，正确率假性偏低。必须走 answerRegexSide。
2. **顶层 decisionItemList** → 漏 80% 话术。必须递归 childrenList。
3. **decisionNodeBO.name** → 是"普通节点"这类标签。必须用 sceneNodeName。
4. **Python re 编译百应正则** → lookbehind 报错。统一 Node/V8。
5. **把"节点内续说"当缺陷** → 把合法顺序话术算成走错。target=None 是树内推进。
6. **回溯到更早可判定 step** → errWrong 虚高。无判定分支直接跳过。
7. **宽松包含匹配知识库** → 19 万虚假命中（"在宜昌。"命中"我在"）。只做正向包含。
8. **弱肯定规则误归因** → `^嗯。$` 属于 `肯定(中性)`，不是所有叫"肯定"的分支。
   改动要精确到全局库分支 ID（同名可能多个）。
9. **语气词当缺口** → "嗯嗯/哦/啊"补词会制造冲突。纯语气占比高的组不补。
10. **在默认分支上找 target** → 只有默认分支的节点走默认是正常的，不是缺陷。

### 模式 B（呼入 IVR）专属坑

11. **barge-in 不合并** → "说人工+按1"混合段被拆开误判（38.5% 伪影）。连续用户轮必须合并成段。
12. **路由判定按单轮** → AI 响应的是整段，段后第一个非空 AI 句（maxskip 6~12，跳空轮）才算。
13. **语境指纹优先级错** → "支付宝问句"含"按键输入身份证"，指纹必须排在身份证输入之前。
14. **D4 放在无语境 continue 之后** → "您好。在吗"不在指纹表，ctx=None 提前 continue，缺陷永远 0。
15. **重问判定逐字相等** → 重问句常不带"好的，"前缀，要用语境指纹相等。
16. **否认词一个版本通吃** → 混合段要搜索版、孤立应答要锚定版；核实环节"不是"是合理重输，不算缺陷。
17. **时间赛跑没排除就归因** → 先比 start_time：AI 重问晚于用户应答结束才可能是识别失败；重叠是 TTS 冲突，另案。
18. **正常设计当缺陷** → 忙提示按1回菜单（继续等待=回主菜单）、菜单外数字不响应、探活"在吗"，都不是缺陷。
19. **工具语境识别失败当缺陷** → 按键（DTMF）输入、远程数据查询等工具期间自然语言不识别是平台默认（TOOL_ONLY_CTXS 豁免），识别失败/无响应忽略；但"工具语境无人工出口"可作为产品建议另提，不进缺陷计数。
20. **无响应≠缺陷** → 多为 DTMF 等待期用户放弃；结合"说人工"等意图且非工具语境才是缺陷。
